## 1. Redis Lua 스크립트로 "주문 꺼내기 + 처리 중 표시"를 원자 실행

### 상황

같은 결제(paymentId)에 대해 **세 요청이 거의 동시에** 들어올 수 있다.

- PC 브라우저의 결제 완료 요청 (`/api/payment/complete`)
- 모바일 결제 후 리디렉션 페이지의 결제 완료 요청
- PortOne 서버의 웹훅 (`Transaction.Paid`) — 결제 직후 바로 오므로 브라우저보다 빠른 경우가 많다

결제 확정은 **정확히 한 번**만 일어나야 한다. 두 번 일어나면 예약이 2건 생기고, 0번이면 돈만 빠져나간다.

### 필요한 연산

```
1. GET  payment:pending:{id}          # 대기 주문 읽기
2. 있으면:
   DEL  payment:pending:{id}          # 다른 요청이 못 가져가게 삭제
   SET  payment:processing:{id} 1 EX 60   # "지금 처리 중" 표시
```

"읽은 결과를 보고 쓸지 말지 정하는" **check-then-act** 연산이다. 이런 연산은 중간에 다른 요청이 끼어들면 깨진다.

### 명령을 따로 보내면 생기는 틈

```
요청 A (웹훅)                          요청 B (사용자 완료 요청)
GETDEL pending  → 주문 획득
                 ─── 틈 ───           GETDEL pending      → 없음
                                       EXISTS processing   → 없음 (A가 아직 SET 전)
                                       예약 조회           → 아직 없음
                                       → "결제 정보를 찾을 수 없습니다" 오류 ✗
SET processing
예약 확정 완료
```

사용자는 결제에 성공했는데 오류 화면을 보게 된다. 틈이 수 ms라도 요청이 몰리면 실제로 발생한다.

### 대안 비교

| 방법 | 원자적인가 | "있을 때만 쓰기" 가능한가 | 문제 |
|---|:---:|:---:|---|
| 명령 3개를 따로 전송 | ✗ | ○ | 위의 틈 |
| `GETDEL` 한 명령 (기존) | ○ | ✗ | 꺼내기는 원자적이지만 처리 중 표시를 함께 남길 수 없음 |
| `MULTI` / `EXEC` (Redis 트랜잭션) | ○ | **✗** | 명령이 큐에 쌓였다가 `EXEC` 때 한꺼번에 실행된다. `GET`의 결과를 `EXEC` 전에 볼 수 없으니 "있으면 SET"을 표현할 수 없다 |
| `WATCH` + `MULTI` | ○ (낙관적) | ○ | 감시하던 키가 바뀌면 `EXEC`가 실패하고 재시도 루프를 직접 짜야 한다. 경쟁이 심할수록 재시도가 늘어난다 |
| 분산 락 (`SET NX` / Redisson) | ○ | ○ | 락 획득·해제·만료·재진입을 관리해야 하고 의존성이 늘어난다. 키 하나 꺼내는 문제에는 과하다 |
| **Lua 스크립트 (`EVAL`)** | **○** | **○** | 조건 분기를 서버에서 한 번에 실행 |

### 왜 Lua는 원자적인가

Redis는 명령을 **단일 스레드 이벤트 루프**에서 하나씩 처리한다. `EVAL`로 보낸 스크립트도 명령 하나로 취급되어, 스크립트가 끝날 때까지 **다른 클라이언트의 명령이 끼어들 수 없다**. 그래서 스크립트 안의 GET → DEL → SET 사이에 틈이 없다.

```lua
local v = redis.call('GET', KEYS[1])            -- KEYS[1] = payment:pending:{id}
if v then
  redis.call('DEL', KEYS[1])
  redis.call('SET', KEYS[2], '1', 'EX', ARGV[1]) -- KEYS[2] = payment:processing:{id}, ARGV[1] = 60
end
return v
```

### 주의할 점 (Lua를 쓸 때 알아야 할 것)

1. **롤백이 없다.** 스크립트 중간에 오류가 나도 앞에서 실행한 쓰기는 그대로 남는다. "원자적"은 끼어들기가 없다는 뜻이지 트랜잭션 롤백이 된다는 뜻이 아니다. 그래서 스크립트는 짧게, 실패할 지점이 없게 작성했다.
2. **긴 스크립트는 Redis 전체를 막는다.** 실행 중에는 다른 모든 요청이 기다린다. 반복문이나 대량 키 처리를 넣으면 안 된다.
3. **키는 `KEYS`, 값은 `ARGV`로 넘긴다.** 스크립트 안에서 키 이름을 문자열로 조립하면 클러스터에서 어느 노드로 보낼지 알 수 없다.
4. **클러스터 모드에서는 모든 키가 같은 해시 슬롯에 있어야 한다.** 아니면 `CROSSSLOT` 오류가 난다. 현재는 단일 노드라 문제없지만, 클러스터로 가면 `payment:{pay_x}:pending`, `payment:{pay_x}:processing`처럼 **해시 태그** `{...}`로 묶어야 한다.
5. **매번 스크립트 원문을 보내지 않는다.** Spring의 `DefaultRedisScript`는 SHA1으로 `EVALSHA`를 먼저 호출하고, 서버 캐시에 없을 때(`NOSCRIPT`)만 원문으로 `EVAL`한다.

### 면접 질문

- **"Redis 트랜잭션(MULTI)으로는 안 되나요?"** → MULTI는 명령을 모아 한 번에 실행할 뿐, 중간 결과로 분기할 수 없다. "주문이 있을 때만 처리 중 표시"는 조건부 쓰기라 Lua나 WATCH가 필요하다. WATCH는 충돌 시 재시도 루프가 필요해 Lua를 택했다.
- **"Lua 스크립트면 트랜잭션처럼 롤백되나요?"** → 아니다. 격리(끼어들기 없음)는 보장하지만 원자적 롤백은 없다.

## 2. "처리 중" 표시와 기다리기

### 왜 필요한가

주문을 꺼낸 쪽이 확정하는 동안(PortOne 조회 + 예약 저장, 보통 1초 이내), 뒤늦게 온 요청은 "주문도 없고 예약도 아직 없는" 상태를 본다. 처리 중 표시가 있으면 뒤 요청은 **실패 대신 기다렸다가** 같은 결과(예약 정보)를 돌려줄 수 있다.

### 설계 값과 이유

| 값 | 이유 |
|---|---|
| 표시 TTL 60초 | 처리 도중 서버가 죽으면 `finish()`가 호출되지 않는다. TTL이 없으면 표시가 영원히 남아 뒤 요청이 계속 기다린다 |
| 200ms 간격, 최대 5초 대기 | 확정은 보통 1초 이내. 너무 촘촘하면 Redis 호출이 늘고, 너무 길면 응답이 늦다 |
| 확정 실패 시 `restore()` | PortOne 조회 실패 같은 일시적 오류는 주문을 되돌리고 표시를 지워 재시도할 수 있게 한다 |

### 대안

- **Redis Pub/Sub으로 완료 알림**: 폴링은 없지만, 구독 연결 관리와 알림 유실 시 대비가 필요하다. 대기가 최대 5초인 이 경우에는 폴링이 단순하다.
- **클라이언트가 재시도**: 서버는 바로 "처리 중(202)"을 응답하고 프론트가 다시 묻는 방식. 더 확장성 있지만 프론트 흐름이 복잡해진다.

### 한계

주문을 꺼낸 뒤 확정 전에 서버가 죽으면 **주문은 사라졌고 PG 결제는 승인된 상태**가 된다. 보상 취소도 실행되지 않는다. 이를 막으려면 PortOne의 결제 목록과 우리 예약을 주기적으로 비교하는 **대사(reconciliation) 배치**가 필요하다. 아직 구현하지 않았다.

## 3. 결제 대기 주문을 Redis에 둔 이유와 서버 금액 계산

### 왜 Redis인가

- 결제창을 열고 이탈하는 사용자가 많다. DB에 저장하면 결제되지 않은 주문이 쌓여 정리 배치가 필요하다. Redis는 **TTL(30분)로 자동 소멸**한다.
- 결제 완료 전까지는 조회·삭제만 하는 임시 데이터라 관계형 모델이 필요 없다.

### 왜 금액을 서버가 계산하는가

기존에는 프론트가 보낸 금액으로 결제창을 열고, 완료 시에도 프론트가 보낸 금액과 PortOne 금액을 비교했다. 사용자가 요청을 조작해 **1원으로 결제하고 1원과 비교**하면 검증을 통과한다. 지금은 `ready`에서 서버가 `가격 × 인원`을 계산해 저장하고, `complete`에서는 **서버가 저장한 금액**과 PortOne 실제 결제 금액을 비교한다.

### BigDecimal은 `compareTo`로 비교

```java
new BigDecimal("15000").equals(new BigDecimal("15000.00"))    // false — scale 까지 비교
new BigDecimal("15000").compareTo(new BigDecimal("15000.00")) // 0 — 값만 비교
```

PortOne 응답(정수)과 DB 값(소수 2자리)의 scale이 다를 수 있으므로 금액 비교는 항상 `compareTo`를 쓴다.

### 한계

Redis가 재시작되면(영속화 설정이 없으면) 대기 주문이 사라진다. 그 사이 결제한 사용자는 "결제 정보 없음"을 보게 된다. AOF 영속화나 2번의 대사 배치로 보완해야 한다.

## 4. 비관적 락과 락 대기 시간

### 왜 비관적 락인가 (측정 근거)

동시 20건, 남은 자리 100석 (Testcontainers MySQL)

| 방식 | 성공 | 실패 |
|---|:---:|---|
| 비관적 락 (`SELECT … FOR UPDATE`) | 20 | 0 |
| 낙관적 락 (`@Version`)만 | 2 | 18 (버전 충돌) |

결제는 "이미 돈을 낸 뒤" 예약을 확정하는 흐름이다. 낙관적 락은 충돌하면 실패시키는 방식이라, 자리가 남아 있어도 90%가 실패하고 PG 자동 취소 후 재결제를 요구하게 된다. 인기 박람회처럼 **같은 행에 요청이 몰리는 곳**에는 줄을 세우는 비관적 락이 맞다.

### `SELECT … FOR UPDATE`는 무엇을 잠그나

InnoDB는 PK 등호 조건(`WHERE expo_id = ?`)이면 **그 행 하나에만** 배타 락을 건다(고유 인덱스 등호 검색이라 갭 락 없음). 락은 트랜잭션이 커밋되거나 롤백될 때까지 유지된다. 다른 박람회 예약은 서로 막지 않는다.

### 락 대기 시간 — JPA 힌트는 MySQL에서 무시된다 (측정으로 발견)

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
```

이 힌트로 "3초 넘게 기다리면 예외"를 의도했지만, Hibernate가 MySQL에 보낸 SQL은 `… for update`뿐이었다. 테스트에서 앞 트랜잭션이 6초 동안 락을 잡자, 뒤 요청은 **6,046ms를 기다린 뒤 락을 얻었다.** 실제 상한은 InnoDB 기본값인 **50초**였다. 결제가 몰리면 요청 스레드와 DB 커넥션이 최대 50초씩 묶여 커넥션 풀이 고갈될 수 있다.

**해결**: 커넥션을 만들 때 세션 변수로 제한했다.

```yaml
spring.datasource.hikari.connection-init-sql: SET SESSION innodb_lock_wait_timeout = 3
```

수정 후에는 **3,031ms 후 `PessimisticLockingFailureException`**이 발생한다. 결제 흐름은 이 예외를 받으면 PG 결제를 자동 취소하고 `R017`(요청이 몰림, 409)로 응답한다.

| 대안 | 판단 |
|---|---|
| `NOWAIT` (MySQL 8) | 기다리지 않고 즉시 실패 — 짧게 줄 서면 처리될 요청까지 실패시킨다 |
| 쿼리 직전에 `SET SESSION`을 실행하는 네이티브 쿼리 | 호출하는 곳마다 챙겨야 해서 누락 위험 |
| MySQL 서버 설정(`my.cnf`) | 앱 밖에 설정이 흩어지고, 같은 DB를 쓰는 배치 작업에도 영향 |
| **커넥션 초기화 SQL** | 앱의 모든 커넥션에 일관 적용, 설정이 코드와 함께 버전 관리됨 |

> 참고: MySQL은 락 대기 타임아웃이 나면 기본적으로 **그 문장만** 롤백한다(`innodb_rollback_on_timeout=OFF`). 이 프로젝트에서는 예외가 `@Transactional` 경계 밖으로 전파되므로 Spring이 트랜잭션 전체를 롤백한다. 예외를 잡아 삼키면 반쯤 반영된 트랜잭션이 커밋될 수 있으니 주의해야 한다.

### 다른 대안: 조건부 UPDATE

```sql
UPDATE expo SET reserved_count = reserved_count + :people
WHERE expo_id = :id AND reserved_count + :people <= max_capacity;   -- 영향받은 행 0 이면 정원 초과
```

락 대기 없이 문장 하나로 정원 검증과 증가가 끝나 처리량은 가장 좋다. 다만 "정원 초과 불가" 규칙이 도메인 객체(`Expo.increaseReservedCount`)가 아닌 SQL에 들어간다. 이 프로젝트는 규칙을 엔티티에 캡슐화하고 같은 트랜잭션에서 예약 행을 함께 만드는 쪽을 택했다. 트래픽이 커지면 이 방식이 좋은 전환 후보다.

### Redis 분산 락을 쓰지 않은 이유

정원 검증과 예약 저장은 **같은 DB 트랜잭션** 안에서 끝나야 한다. Redis 락은 DB 트랜잭션과 경계가 다르다. 커밋 전에 락이 만료되거나, 락을 푼 뒤 커밋되기 전의 틈에 다른 요청이 옛 값을 읽을 수 있다. 이를 막으려면 펜싱 토큰 등이 필요하다. 단일 DB라면 DB 락이 가장 정확하고 단순하다.

### `@Version`을 함께 두는 이유

관리자가 박람회 정보를 수정하는 경로처럼 비관적 락을 쓰지 않는 곳에서 **갱신 손실(lost update)**을 막는 안전망이다. 테스트에서 낙관적 락만으로도 최종 인원이 성공 건수와 정확히 일치했다(갱신 손실 0).

## 5. 보상 트랜잭션과 트랜잭션 분리

### 왜 보상 트랜잭션인가

PG 결제는 외부 시스템이라 DB 트랜잭션에 넣을 수 없다. "결제 승인 → 예약 저장" 중 예약 저장이 실패하면, DB는 롤백되지만 **PG 결제는 이미 승인된 상태**로 남는다. 그래서 실패를 감지하면 PG 취소 API를 호출해 결과를 되돌린다(보상, compensation).

```
PaymentServiceImpl.confirm()                  ← 트랜잭션 없음
 ├─ PortOne 결제 조회·금액 검증                  (외부 호출)
 ├─ ReservationCompletionService.complete()   ← @Transactional (결제·락·예약·QR 저장)
 └─ 실패하면 cancelSafely() → PortOne 결제 취소   (외부 호출)
```

### 왜 예약 확정을 다른 클래스(빈)로 분리했나 — self-invocation

`@Transactional`은 스프링이 만든 **프록시 객체**가 메서드 호출을 가로채 트랜잭션을 연다. 같은 클래스 안에서 `this.complete()`처럼 호출하면 프록시를 거치지 않아 **트랜잭션이 적용되지 않는다.** 예약 확정만 트랜잭션으로 묶고 그 바깥에서 예외를 잡아 PG를 취소하려면, 트랜잭션 메서드가 다른 빈에 있어야 한다.

### 왜 PG 호출을 트랜잭션 밖에 두나

트랜잭션 안에서 외부 API를 호출하면 응답을 기다리는 동안 **DB 커넥션을 계속 점유**한다. PG가 느려지면 커넥션 풀이 고갈되어 결제와 무관한 조회까지 멈춘다. 그래서 외부 호출은 트랜잭션 밖에 두고, 트랜잭션은 DB 작업만 짧게 유지한다.

### 한계

- **보상 취소 자체가 실패할 수 있다.** 지금은 `ERROR` 로그를 남겨 운영자가 수동으로 환불하는 방식이다. 실패한 취소를 저장해 재시도하는 큐가 필요하다.
- 2번에서 말한 "확정 도중 서버 종료"는 보상도 실행되지 않으므로 대사 배치로 잡아야 한다.

## 6. 커밋 후 비동기 메일 — `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`

### 왜 트랜잭션 안에서 메일을 보내지 않나

1. **메일 실패가 결제를 롤백시킨다.** SMTP 인증 실패(실제로 겪은 535 오류) 같은 문제로 이미 결제된 예약이 롤백되면 안 된다.
2. **SMTP 응답(수백 ms~수 초) 동안 DB 커넥션을 점유한다.**
3. **롤백된 예약에 대해 메일이 나가면 안 된다.** 트랜잭션 안에서 보내면, 메일은 나갔는데 이후 단계가 실패해 예약이 롤백되는 상황이 생긴다.

### 왜 `AFTER_COMMIT`인가

`@TransactionalEventListener(phase = AFTER_COMMIT)`는 트랜잭션이 **커밋에 성공했을 때만** 이벤트를 전달한다. 롤백되면 메일도 나가지 않는다. 일반 `@EventListener`는 발행 즉시 같은 트랜잭션 안에서 실행되므로 위 문제를 그대로 가진다.

### 왜 `@Async`까지 붙이나

`AFTER_COMMIT` 리스너는 커밋 직후 **요청 스레드에서** 실행된다. `@Async`가 없으면 사용자는 메일 발송이 끝날 때까지 결제 완료 응답을 기다린다.

### 한계와 다음 단계

- **커밋 후 메일 전송 전에 서버가 죽으면 메일이 유실된다.** 이벤트가 메모리에만 있기 때문이다. 확실히 보내야 하면 **트랜잭셔널 아웃박스**가 필요하다. 같은 트랜잭션에서 `outbox` 테이블에 "보낼 메일"을 저장하고, 별도 워커가 읽어 발송·재시도하는 방식이다.
- `@Async`는 스프링 부트 기본 스레드 풀(대기 큐 무제한)을 쓴다. 메일이 몰리면 큐가 계속 늘어나므로 전용 풀과 큐 상한을 두는 것이 좋다.

## 7. 웹훅 서명 검증

### 원리 — HMAC

PortOne과 우리만 아는 시크릿으로 `HMAC-SHA256("{webhook-id}.{timestamp}.{body}")`를 계산해 헤더로 보낸다. 우리도 같은 계산을 해서 일치하면 "PortOne이 보냈고 중간에 바뀌지 않았다"고 판단한다. 일반 해시(SHA-256)는 시크릿이 없어 누구나 만들 수 있으므로 **키가 있는 HMAC**이어야 한다.

### 세부 결정

| 결정 | 이유 |
|---|---|
| `@RequestBody String`으로 원문 수신 | DTO로 받으면 역직렬화 후 다시 직렬화할 때 공백·필드 순서가 달라져 서명이 맞지 않는다. 검증은 **받은 바이트 그대로** 해야 한다 |
| `MessageDigest.isEqual`로 비교 | `String.equals`는 첫 번째로 다른 글자에서 바로 반환한다. 공격자가 응답 시간 차이로 한 글자씩 맞춰 가는 **타이밍 공격**이 가능하다. `isEqual`은 길이만큼 항상 끝까지 비교한다 |
| 타임스탬프 ±5분 | 가로챈 정상 웹훅을 나중에 다시 보내는 **재전송 공격** 차단. 서명에 타임스탬프가 포함되어 있어 값을 바꾸면 서명이 깨진다 |
| 서명 여러 개 허용 (`v1,a v1,b`) | 시크릿 교체 기간에는 옛 키와 새 키 서명이 함께 온다 |
| 시크릿 미설정 시 전부 거부 | "설정이 없으면 검증 생략"은 운영에서 설정을 빠뜨렸을 때 무방비가 된다. 실패하는 쪽이 안전하다(fail-closed) |

### 응답 코드 전략

| 상황 | 응답 | 이유 |
|---|---|---|
| 서명 실패 | 401 | 처리하지 않음 |
| 처리 대상이 아닌 이벤트 (Ready 등) | 200 `ignored` | 200이 아니면 PortOne이 계속 재전송한다 |
| 이미 확정된 결제 | 200 | 멱등 — 여러 번 와도 같은 결과 |
| PortOne 조회 일시 실패 | 5xx | 재전송을 받아 다시 처리하도록 의도적으로 실패 응답 |

### 한계

같은 이벤트가 동시에 두 번 오면 둘 다 서명 검증을 통과한다. 다만 1번의 원자적 꺼내기로 한 번만 처리된다. `webhook-id`를 Redis에 잠시 저장해 **중복 이벤트를 입구에서 걸러내는** 방법도 있다.

## 8. 리프레시 토큰 설계

### 왜 JWT가 아닌 UUID(불투명 토큰)인가

JWT 리프레시 토큰은 서명만 맞으면 만료 전까지 유효해서 **즉시 폐기가 어렵다**(블랙리스트를 따로 둬야 함). UUID는 의미 없는 난수이고 유효성이 **전적으로 서버 저장소**에 달려 있다. 저장소에서 지우면 즉시 무효가 되어 로그아웃·비밀번호 재발급 시 세션을 끊기 쉽다.

### 왜 계정 종류를 키에 넣었나

불투명 토큰은 저장소가 곧 신원이다. 이 시스템은 사용자 테이블이 3개이고 id가 서로 겹친다. 그래서 `id=1`은 식별자가 될 수 없고 `(계정 종류, id)` 쌍이 식별자다. 이걸 빠뜨려 **참관객 토큰으로 시스템관리자 토큰이 발급되는 권한 상승**이 있었다.

```
refresh:{TYPE}:{id}     → 토큰        (계정당 1개)
refresh:owner:{token}   → "{TYPE}:{id}" (역인덱스: 토큰으로 주인 찾기)
```

### 역인덱스가 있는데 왜 현재 토큰과 다시 비교하나

```java
String current = redis.get("refresh:" + type + ":" + id);
return refreshToken.equals(current) ? Optional.of(owner) : Optional.empty();
```

재발급·로그아웃 때 역인덱스를 지우지만, 삭제 누락이나 동시 요청이 있으면 옛 역인덱스가 남을 수 있다. **계정의 현재 토큰과 일치할 때만** 유효로 보면, 역인덱스가 남아 있어도 폐기된 토큰은 통과하지 못한다(이중 확인).

### 토큰 회전

재발급할 때마다 새 리프레시 토큰을 주고 이전 것은 폐기한다. 탈취된 토큰은 정상 사용자가 한 번 재발급하면 무효가 된다.

### 한계

- **재사용 탐지 미구현.** 이미 폐기된 토큰으로 재발급을 시도하면 탈취를 의심해 그 계정의 모든 세션을 끊는 방식이 권장된다(OAuth 2.0 Security BCP).
- 토큰을 localStorage에 저장해 XSS에 노출된다. 리프레시 토큰은 HttpOnly 쿠키로 옮기는 편이 안전하다.

## 9. 결제 채널 Strategy

### 왜 Strategy인가

PG사·결제수단마다 결제창 파라미터가 다르다(토스페이는 `EASY_PAY` + `easyPayProvider`, 이니시스 카드는 `CARD`). `if (channel == TOSSPAY) … else if …` 분기는 PG가 추가될 때마다 기존 코드를 고쳐야 한다. 전략 인터페이스로 나누면 **새 PG는 클래스 하나만 추가**하고 기존 코드는 건드리지 않는다(개방-폐쇄 원칙).

### 세부 결정

| 결정 | 이유 |
|---|---|
| `EnumMap<PaymentChannelType, Strategy>` 등록부 | enum 키 조회에 최적화된 배열 기반 맵. 스프링이 주입한 전략 목록을 타입별로 모은다 |
| 설정에 맞는 전략이 없으면 **기동 실패** | 잘못된 설정을 결제 시점(사용자가 결제 버튼을 누를 때)이 아니라 배포 시점에 발견 |
| 파라미터를 서버가 결정해 프론트에 전달 | 채널을 바꿀 때 프론트를 다시 배포할 필요가 없다. 채널 정보가 서버 한 곳에만 있다 |

## 10. N+1 해결 도구 선택

| 도구 | 쓰는 곳 | 주의점 |
|---|---|---|
| 페치 조인 (`JOIN FETCH`) | 단건·소량 조회, `@ManyToOne` | **컬렉션 페치 조인 + 페이징**은 Hibernate가 전체 결과를 메모리로 가져와 자른다(HHH90003004 경고). 목록 페이지에는 부적합 |
| `@EntityGraph` | 페치 조인을 어노테이션으로 | 페치 조인과 같은 제약 |
| `default_batch_fetch_size` | 페이징 목록의 지연 로딩 연관 | 연관을 `IN (?, …)` 한 번으로 가져온다. **페이징을 깨지 않고** 전역 설정 한 줄로 적용 |
| DTO 프로젝션 (`SELECT new …`) | 읽기 전용 목록 | 필요한 컬럼만 조회하고 엔티티·영속성 컨텍스트를 만들지 않는다. 연관 로딩 자체가 없다 |
| GROUP BY 집계 쿼리 | 행마다 "최신값" 조회 | 서비스 코드의 반복 호출은 설정으로 못 막는다. 쿼리를 다시 설계해야 한다 |

- **배치 크기 100**: 페이지 크기(10~20)보다 충분히 크면 한 번에 끝난다. 너무 크면 IN 절이 길어져 DB가 실행 계획을 세우는 비용이 늘어난다.
- **집계는 DB에서**: 합계를 위해 엔티티 1,091개를 만들면 메모리·전송량·GC 부담이 데이터에 비례해 증가한다. `COALESCE(SUM(...), 0)`은 행이 없을 때 `SUM`이 `NULL`을 반환하는 것을 막는다.

## 11. 테스트 전략

### 왜 H2가 아니라 Testcontainers(MySQL)인가

동시성 테스트의 대상은 **InnoDB의 락 동작**이다. H2는 MySQL 호환 모드여도 락 구현, `FOR UPDATE` 동작, `innodb_lock_wait_timeout` 같은 설정이 다르다. 4번의 "JPA 락 타임아웃 힌트가 MySQL에서 무시된다"는 사실도 **실제 MySQL로 측정해서** 발견했다. H2였다면 알 수 없었다.

### 동시성 테스트의 세부 장치

| 장치 | 이유 |
|---|---|
| `@Transactional(propagation = NOT_SUPPORTED)` | `@DataJpaTest`는 기본적으로 테스트 전체를 트랜잭션으로 감싸고 롤백한다. 그러면 테스트가 저장한 데이터가 커밋되지 않아 다른 스레드에서 보이지 않는다 |
| 스레드마다 `TransactionTemplate` | 실제 결제처럼 요청마다 독립된 트랜잭션을 커밋 |
| `CountDownLatch` 두 개 (ready / start) | 스레드 생성 시간 차이로 사실상 순차 실행되는 것을 막는다. 모두 준비된 뒤 **동시에 출발** |
| 불변식 검증 | 낙관적 락처럼 결과가 매번 다를 수 있는 경우 "성공 + 충돌 = 20", "최종 인원 = 성공 수"처럼 항상 참인 조건을 검증해 테스트가 흔들리지 않게 한다 |

### 단위 테스트에서 검증한 것

외부 API(PortOne)와 저장소를 Mockito로 대체하고 **분기마다 부작용**을 확인했다. 예: 금액이 다르면 "PG 취소가 정확한 금액으로 호출되고, 예약 저장은 호출되지 않는다". 결과 값만이 아니라 "호출되지 않아야 할 것"을 `never()`로 확인하는 것이 보상 로직 테스트의 핵심이다.

## 13. 시크릿 관리

| 결정 | 이유 |
|---|---|
| yml에 기본값 없는 `${JWT_SECRET}` | 기본값이 있으면 설정을 빠뜨려도 **공개된 기본값으로 조용히 동작**한다(QR 서명키 `change-me`가 그랬다). 없으면 기동 실패가 낫다 |
| compose의 `${VAR:?메시지}` | 스프링이 뜨기도 전에 compose 단계에서 무엇이 빠졌는지 알려준다 |
| `spring.config.import: optional:file:../.env[.properties]` | IDE 실행과 docker가 **같은 `.env` 하나**를 쓴다. `[.properties]`는 확장자가 없는 파일을 properties 형식으로 읽으라는 힌트다 |
| healthcheck에 `$$MYSQL_PASSWORD` | `$$`는 compose가 치환하지 않고 컨테이너 셸의 환경변수로 넘긴다. compose 파일에 비밀번호를 쓰지 않는다 |

> 파일에서 지워도 git 이력에는 남는다. 커밋된 적 있는 시크릿은 "노출된 것"으로 보고 **교체**하는 것이 원칙이다.

## 14. 역할별 토큰 키 단일화 (시스템관리자 로그인 불가 버그)

토큰 저장 키가 로그인 화면·`AuthContext`·axios·로그아웃 버튼 4곳에 각자 정의되어 있었다. 시스템관리자 토큰을 박람회관리자 키에 저장하고 axios는 시스템관리자 키에서 읽어서, **로그인 API는 성공하지만 모든 요청에 토큰이 붙지 않았다.** 이 버그는 `/api/sys/**`가 인증 없이 열려 있던 동안 드러나지 않았고, 인증을 적용하자 로그인 불가로 나타났다.

`auth/tokenKeys.js` 한 파일에 역할별 키·재발급 URL·로그아웃 경로를 두고 모든 코드가 이 파일만 쓰게 했다(**단일 진실 공급원, SSOT**). 로그인할 때는 다른 역할의 토큰을 먼저 모두 지운다. 여러 역할의 토큰이 남아 있으면 요청마다 어떤 토큰이 붙을지 예측하기 어렵기 때문이다.

> 교훈: 인증을 강화하는 변경은 **실제 로그인 화면부터 API 호출까지** 이어서 검증해야 한다. 브라우저 테스트에서 토큰을 직접 넣으면 "토큰을 어디에 저장하는가"라는 경로 자체를 건너뛴다.

### 401 응답을 받았을 때 "누구의 401인가"를 먼저 구분한다

axios 응답 인터셉터는 401/403을 받으면 토큰을 재발급하고 원래 요청을 다시 보낸다. 그런데 401은 여러 상황에서 온다.

- **로그아웃한 뒤 도착한 응답**: 로그아웃 순간 대기 중이던 요청은 블랙리스트된 토큰 때문에 401을 받는다. 이때 재발급을 시도하면 리프레시 토큰이 이미 없어 실패하고, 실패 처리 코드가 페이지를 강제로 새로고침했다.
- **다른 요청이 이미 재발급한 경우**: 동시에 나간 요청 여러 개가 모두 옛 토큰으로 401을 받는다. 재발급은 한 번만 해야 한다(기존 코드는 Promise를 공유해 직렬화). 재발급이 끝난 뒤 도착한 401은 재발급 없이 새 토큰으로 다시 보내면 된다.

그래서 **요청에 실어 보낸 토큰과 지금 저장된 토큰을 비교**해, 보낸 토큰이 있는데 지금 없으면 조용히 실패시키고, 서로 다르면 새 토큰으로 한 번만 재시도한다. "이 응답이 지금 세션의 응답인가"를 판단하는 기준을 요청 자체에 둔 것이다.
